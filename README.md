# PIRSky

# Efficient and Private Location-Based Skyline Retrieval via Compressed Conservative Grid Materialization

This repository contains an experimental pipeline for **materializing location-based skyline candidates into a compressed grid database** and evaluating **single-record retrieval with a Piano-style PIR prototype**.

The workflow has two parts:

1. **Sky / GRID database generation (Python)** — build a unified global fine grid, compress it with Direct (`mode1`) or Hybrid (`mode2`), and export a fixed-record database.
2. **GRID database retrieval (Go)** — load the exported database and metadata, emulate Piano's hint-based PIR retrieval, and record computation, communication-payload, and memory metrics.

> \\\*\\\*Research-prototype scope.\\\*\\\* The Go program runs the client and server computations locally in one process. It does \\\*\\\*not\\\*\\\* establish a client–server network connection. Reported times are local computation times, while communication byte counts are estimates from the message structure, not measured network traffic. The code is not a production security deployment.

## 1\. Source files

|File|Purpose|
|-|-|
|`SkyAgg\\\_GRID\\\_DB.py`|Generates the global fine grid, constructs the Direct/Hybrid compressed grid, and exports the PIR database and metadata. Also supports `locate` and `decode` debugging commands.|
|`batch\\\_build.py`|Batch-runs `SkyAgg\\\_GRID\\\_DB.py build` over `./data/dataset/\\\*.txt`, collects logs, and samples system memory.|
|`tutorial\\\_griddb\\\_metrics.go`|Loads the generated `.pir.db` and `.pir.meta.json` files, executes a local Piano-style hint-based retrieval, checks the recovered record, and reports metrics.|
|`run\\\_go\\\_batch.sh`|Iterates over existing GRID database files, runs the Go benchmark repeatedly (10 times by default), and saves task-specific logs and JSON results.|

## 3\. Dataset format

Input is a plain-text CSV-like file with **one point per line**, comma-separated numeric attributes and **no header**:

```text
1,3,1
2,1,2
3,2,1
2,2,3
```

The first two attributes are spatial coordinates `x,y`; any additional attributes are non-spatial. All nonempty data rows must have the same number of attributes. Point IDs are assigned automatically, starting from `1`, in file order. Blank lines and lines starting with `#` are ignored.

Example dataset naming convention:

```text
<d>\\\_<n>\\\_<TYPE>.txt
2\\\_1000\\\_ANTI.txt
```

`TYPE` is conventionally one of `ANTI`, `CORR`, `INDE`, `HOS`, `STR`, or `VEH`. The scripts **do not infer dimensions from filenames**: the point dimensions come from the file contents. As used in the experiments, a leading dataset label such as `2` should be treated as a dataset identifier/experimental dimension label, not as a hard-coded parser flag.

By default, `SkyAgg\\\_GRID\\\_DB.py` builds a domain whose lower spatial boundary is `0`; negative spatial coordinates require `--no-origin-left`.

## 4\. Generate a GRID database (Python)

### 4.1 Direct compression (`mode1`)

```bash
python SkyAgg\\\_GRID\\\_DB.py build \\\\
  --data ./data/dataset/2\\\_1000\\\_ANTI.txt \\\\
  --mode mode1 \\\\
  --compression 10 \\\\
  --pi-avg 0.75 --pi-min 0.50 \\\\
  --export-prefix /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode1\\\_75\\\_50
```

`mode1` builds the compressed grid once, using high-weight horizontal/vertical boundaries computed from Jaccard distances between neighboring fine-cell candidate sets. It controls the **initial grid size**, but does not guarantee that the reported candidate-expansion budgets are satisfied.

### 4.2 Hybrid compression (`mode2`)

```bash
python SkyAgg\\\_GRID\\\_DB.py build \\\\
  --data ./data/dataset/2\\\_1000\\\_ANTI.txt \\\\
  --mode mode2 \\\\
  --compression 10 \\\\
  --pi-avg 0.95 --pi-min 0.90 \\\\
  --max-iter 25 \\\\
  --export-prefix /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90
```

`mode2` starts with a Direct grid, evaluates `total\\\_positive\\\_error` and `max\\\_cell\\\_extra`, and searches for a finer grid if the prescribed budgets are violated. **Important:** if no budget-satisfying grid is found within the search limit, the current implementation warns and returns the initial Direct grid; always inspect the log instead of assuming both constraints were met.

Important build options:

|Option|Default|Meaning|
|-|-|-|
|`--data`|`points.txt`|Input dataset.|
|`--mode`|`mode2`|`mode1` = Direct; `mode2` = Hybrid.|
|`--compression`|`10.0`|Target ratio `fine\\\_cells / target\\\_coarse\\\_cells`; a larger value requests fewer coarse cells.|
|`--max-coarse-cells`|unset|Overrides the compression-derived target cell budget.|
|`--min-cols`, `--min-rows`|`10`, `10`|Minimum requested coarse grid resolution, clipped to the fine grid shape.|
|`--pi-avg`, `--pi-min`|`0.75`, `0.50`|Targets used to calculate global/per-cell candidate-expansion budgets.|
|`--max-iter`|`25`|Maximum Hybrid refinement iterations.|
|`--query QX QY`|unset|Optionally generate a query-index JSON and run local correctness/debug checks during build.|
|`--export-prefix`|`./out/skyagg\\\_griddb`|Output filename prefix.|
|`--no-origin-left`|off|Start the domain at minimum observed coordinates rather than `0`.|
|`--no-conservative-boundary`|off|Disable additional conservative boundary inclusion in transformed quadrants.|

### 4.3 Exported files

For a prefix `PREFIX`, the Python builder creates:

```text
PREFIX.pir.db
PREFIX.pir.meta.json
PREFIX.query.json        # only when --query is supplied
```

* **`.pir.db`**: binary array of fixed-length records (little-endian unsigned 64-bit words), with no file header.
* **`.pir.meta.json`**: `db\\\_records`, `record\\\_words`, spatial grid edges, coarse partition blocks, index ordering, and a copy of the input point IDs/attributes.
* **`.query.json`**: optional local query location, grid coordinates, and PIR index.

Each final coarse cell corresponds to exactly one PIR record. The record layout is:

```text
\\\[count, point\\\_id\\\_1, ..., point\\\_id\\\_count, 0, ..., 0]
```

All records have the same length:

```text
record\\\_words = 1 + max\\\_candidate\\\_count\\\_over\\\_all\\\_coarse\\\_cells
record\\\_bytes = record\\\_words \\\* 8
DB\\\_file\\\_bytes = db\\\_records \\\* record\\\_bytes
```

The record order is **column-major in the grid**:

```text
pir\\\_index = grid\\\_col \\\* grid\\\_num\\\_rows + grid\\\_row
```

Thus a query position is located locally as `q -> (grid\\\_col, grid\\\_row) -> pir\\\_index`.

> \\\*\\\*Metadata caveat:\\\*\\\* the current `.pir.meta.json` also includes a `points` array containing all original point coordinates and attributes. It is a builder/debug metadata file, \\\*\\\*not\\\*\\\* a privacy-minimal client-side metadata package. For a real outsourced deployment, separate the public grid-index metadata from private source data before distribution.

### 4.4 Locate and debug a record without PIR

```bash
python SkyAgg\\\_GRID\\\_DB.py locate \\\\
  --meta /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.meta.json \\\\
  --query 2.0 2.0 \\\\
  --out /Sky/example.query.json

python SkyAgg\\\_GRID\\\_DB.py decode \\\\
  --db /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.db \\\\
  --meta /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.meta.json \\\\
  --index 0
```

`decode` reads a record directly from disk and **does not perform PIR**.

## 5\. Batch GRID generation (Python)

Configure `batch\\\_build.py` before running:

```python
# in main()
data\\\_dir = "./data/dataset/"
modes = \\\["mode1", "mode2"]
param\\\_sets = \\\[
    {"name": "Default", "pi\\\_avg": 0.75, "pi\\\_min": 0.50},
    {"name": "Strict", "pi\\\_avg": 0.95, "pi\\\_min": 0.90},
]
# in run\\\_build(...)
export\\\_prefix = "/Sky/skyagg\\\_griddb"
```

Run:

```bash
python -m pip install psutil
python batch\\\_build.py
```

The script writes `./logs/build\\\_log\\\_<timestamp>.txt` and exports each dataset/mode/precision pair using the naming convention:

```text
/Sky/skyagg\\\_griddb\\\_<d>\\\_<n>\\\_<TYPE>\\\_<mode>\\\_<avg>\\\_<min>.pir.db
/Sky/skyagg\\\_griddb\\\_<d>\\\_<n>\\\_<TYPE>\\\_<mode>\\\_<avg>\\\_<min>.pir.meta.json
```

**Important behavior of the supplied batch script:**

* The only *enabled* parameter set is currently `Default` (`75\\\_50`), and the code contains `if mode == "mode2" and param\\\_set\\\["name"] == "Default": continue`. As supplied, it **runs only mode1**, despite listing both modes. To benchmark mode2, enable a non-Default setting (e.g. `Strict`) or adjust that condition.
* `total\\\_tasks` is currently hard-coded as two tasks per input file and can overcount the jobs actually executed.
* The memory monitor samples **system-wide used physical RAM** every 0.5 s, not the Python child's peak RSS. Interpret its `峰值内存` value accordingly.
* The script captures stdout/stderr into the batch log; it may not echo full build output to the terminal.

## 6\. Run Piano-style GRID retrieval (Go)

Place `tutorial\\\_griddb\\\_metrics.go` in the **Piano-PIR module root** and run there so that the `example.com/util` import resolves through the project's `go.mod`.

### 6.1 Retrieve by database index

```bash
go run tutorial\\\_griddb\\\_metrics.go \\\\
  -db /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.db \\\\
  -meta /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.meta.json \\\\
  -index 0 \\\\
  -show-ids \\\\
  -metrics-json /Sky/cost/example\\\_metrics.json
```

Create `/Sky/cost` first if necessary. Each invocation loads the database, performs Piano-style hint setup, generates an expanded request set, computes the server XOR parity, recovers the requested record, and checks it against `FullDB\\\[index]`.

### 6.2 Retrieve by query coordinates

```bash
go run tutorial\\\_griddb\\\_metrics.go \\\\
  -db /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.db \\\\
  -meta /Sky/skyagg\\\_griddb\\\_2\\\_1000\\\_ANTI\\\_mode2\\\_95\\\_90.pir.meta.json \\\\
  -qx 2.0 -qy 2.0 \\\\
  -metrics-json /Sky/cost/query\\\_metrics.json
```

Alternatively, use `-query-json /Sky/example.query.json` generated by the Python `locate` command. `-index`, `-qx/-qy`, and `-query-json` are alternative ways of selecting the target; when multiple are supplied, `-query-json` takes precedence, followed by `-index`.

Other Go flags: `-seed` (default `1`), `-show-ids` (default `false`), `-metrics-json` (optional).

**Benchmark details:** database records are represented as `\\\[]uint64`, and XOR is applied across all words in each record. Each run starts with a fresh hint setup. The Go program does not itself perform the final location-based skyline refinement; it returns the stored candidate IDs.

### 6.3 Metrics

The console and optional JSON output include:

|Metric|Interpretation|
|-|-|
|`DB records`, `record\\\_words`, `skyline\\\_count`|Database records, fixed record length, retrieved candidate count.|
|`load\\\_db`|Local binary database loading time.|
|`setup`|Hint/preprocessing construction time.|
|`client\\\_find`|Hint search and expanded-query preparation time.|
|`server\\\_compute`|Local server-side XOR aggregation time.|
|`client\\\_recover`|Record recovery, verification, cache/hint-update time.|
|`online\\\_total`|Sum of `client\\\_find + server\\\_compute + client\\\_recover`, **without network delay**.|
|`end\\\_to\\\_end`|Whole local invocation including DB loading and setup.|
|`setup\\\_download\\\_bytes`|Estimated initial database-sized download payload.|
|`online\\\_request\\\_bytes`|Estimated query-index payload (`ChunkNum \\\* 8`).|
|`online\\\_response\\\_bytes`|Estimated single-record payload (`record\\\_words \\\* 8`).|
|`online\\\_total\\\_bytes`|Request plus response payload estimate.|
|`client\\\_hint\\\_storage`|Estimated client hint storage, not an exact runtime heap measurement.|
|`before\\\_setup`, `after\\\_setup`, `after\\\_query`|Go heap snapshots from `runtime.MemStats`.|

The source uses `ChunkSize = ceil(sqrt(db\\\_records))` and `ChunkNum = ceil(db\\\_records / ChunkSize)`, padding the in-memory database with zero vectors to complete the final chunk. **Do not interpret estimated communication bytes as measured network communication or these local times as end-to-end client–server latency.**

## 7\. Batch Piano retrieval (shell)

The supplied `run\\\_go\\\_batch.sh` expects existing database/metadata pairs in `/Sky` and uses the following configuration near the top of the file:

```bash
GO\\\_PROGRAM="tutorial\\\_griddb\\\_metrics.go"
INTPUT\\\_DIR="/Sky"             # spelling in the supplied script
OUTPUT\\\_DIR="/Sky/cost"
NUM\\\_ITERATIONS=10
D\\\_VALUES=(1)
N\\\_VALUES=(10000 100000)
TYPE\\\_VALUES=(CORR INDE ANTI HOS STR VEH)
PE\\\_VALUES=("1\\\_75\\\_50" "2\\\_95\\\_90")
```

Here `PE\\\_VALUES=("1\\\_75\\\_50" "2\\\_95\\\_90")` produces files containing `mode1\\\_75\\\_50` and `mode2\\\_95\\\_90` respectively. Adjust the arrays to the experiments actually built.

Run from the Piano module root:

```bash
chmod +x run\\\_go\\\_batch.sh
./run\\\_go\\\_batch.sh
```

One logical task (`d`, `n`, distribution, mode/precision) is run `NUM\\\_ITERATIONS` times. Its outputs are:

```text
/Sky/cost/run\\\_<d>\\\_<n>\\\_<TYPE>\\\_mode<mode>\\\_<avg>\\\_<min>.log
/Sky/cost/piano\\\_metrics\\\_<d>\\\_<n>\\\_<TYPE>\\\_mode<mode>\\\_<avg>\\\_<min>.json
```

The JSON file contains an **array of iteration results**, not a file of precomputed averages. Failed iterations are reported in the log; analyze only successful iterations.

### Important: fix the random-index range before batch benchmarking

As supplied, `run\\\_go\\\_batch.sh` generates the random index as `random % (Data\\\_range \\\* Data\\\_range)` with `Data\\\_range=1000`, regardless of the current database size. In the Go program, an out-of-range `-index` is silently reduced modulo `DBSize`. That makes the sampled index distribution potentially biased.

For a representative batch benchmark, replace the index generation with sampling based on each current metadata file's **actual** `db\\\_records`. For example, from the shell script's `run\\\_go\\\_command()` loop:

```bash
local DB\\\_RECORDS
DB\\\_RECORDS=$(python3 -c 'import json,sys; print(json.load(open(sys.argv\\\[1]))\\\["db\\\_records"])' "$META\\\_PATH")
# Simple modulo sampling (suitable for benchmark convenience):
local random\\\_index=$(( $(od -An -N4 -tu4 /dev/urandom | tr -d ' ') % DB\\\_RECORDS ))
```

Use this in place of `local random\\\_index=$(gen\\\_random\\\_index)` within the iteration loop (the `DB\\\_RECORDS` assignment must occur **before** that loop). For exact uniform sampling, use Python's `secrets.randbelow(DB\\\_RECORDS)` instead of modulo reduction. The code above intentionally documents the required change; it is not already applied to the uploaded `.sh` file.

## 9\. Interpretation and limitations

1. **Conservative candidates, not necessarily final skylines.** Coarse cells store unions of fine-cell candidate sets, so compression does not remove a candidate that was in the source fine cell. Exact per-query skyline results require local refinement using the original query and the relevant attributes.
2. **Dimensional semantics.** The current grid builder accepts two spatial coordinates and additional non-spatial attributes, but its bundled `refine\\\_global\\\_skyline\\\_from\\\_candidates()` comparison uses quadrant membership and the **two spatial distances only**. The multidimensional skyline guarantee must therefore be checked against the precise dominance definition used in the paper before claiming end-to-end exactness for `d > 2`.
3. **Hybrid budget limitations.** `mode2` may fall back to the initial Direct grid if its search finds no satisfying grid within the iteration cap. Check `max\\\_total\\\_error`, `max\\\_cell\\\_error`, and the final grid diagnostics.
4. **Static materialization.** No incremental point insertion/deletion or dynamic grid maintenance is implemented.
5. **PIR protocol measurement scope.** The Go benchmark is a single-process experimental adaptation with simulated client/server operations. It does not measure real network RTT, TCP framing, or a deployed authenticated channel. Its local full-DB consistency check is an experimental assertion, **not** a cryptographic authentication protocol against a malicious server.
6. **Security metadata separation.** Do not ship the builder's full `.pir.meta.json` to privacy-sensitive clients unchanged, because it includes the underlying dataset's `points` field. Extract only the public grid mapping information needed to locate PIR indices.

## 10\. Reproducibility checklist

* Record the dataset filename, number of points, number of attributes, mode, precision values, and compression target.
* Save both `.pir.db` and `.pir.meta.json` and verify the metadata's `db\\\_records` and `record\\\_words`.
* For `mode2`, confirm both reported candidate-expansion budgets were met (or disclose fallback).
* Run Go benchmarks with an index satisfying `0 <= index < db\\\_records`.
* State whether times are local computation only; report network communication separately only if network channels were actually used.
* Average repeated iterations for charts, and report the number of successful iterations.

The retrieval prototype is adapted from the **Piano** single-server PIR tutorial. The work here focuses on producing a compact, conservative, PIR-addressable skyline GRID database and evaluating its retrieval costs; it does not introduce a new PIR cryptographic protocol.
